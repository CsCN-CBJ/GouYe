# 开发纪律

本文件定义 AI 在实现代码时必须自动遵守的行为规则。无需用户触发，每次写完/改完代码后自动执行。

## 实现后自动 Self-Review

每次完成代码修改后（无论大小），在报告完成之前，必须执行以下检查：

### Pass 1: Spec 合规检查

逐条对照用户的需求/任务描述：

- 实现了所有被要求的功能（不遗漏）
- 没有实现未被要求的功能（不私加）
- 接口签名、数据格式与约定一致
- 没有偷偷"改进"相邻代码

**不信任自己的直觉**：重新读一遍需求原文，逐条核对代码。如果发现偏差，立即修复。

### Pass 2: 代码质量检查

| 检查项 | 严重度 | 说明 |
|--------|--------|------|
| 硬编码配置 | Critical | URL、端口、密钥、超时等必须走环境变量或配置文件 |
| 吞异常 | Critical | 不允许空 catch/except，失败路径必须有明确行为 |
| 无限循环/阻塞 | Critical | 所有循环和阻塞调用必须有上限或超时 |
| 单一职责 | Important | 每个函数/类只做一件事 |
| 命名清晰 | Important | 变量名让不看上下文的人也能理解 |
| 错误处理 | Important | 外部输入不信任，有校验或兜底 |
| 测试覆盖 | Important | 新逻辑有对应测试，测试验证行为而非实现细节 |
| 重复代码 | Minor | 相同逻辑出现 2 次以上应提取 |

### Pass 3: 发现问题的处理

- **Critical** → 立即修复，不问用户
- **Important** → 立即修复，不问用户
- **Minor** → 顺手修复，不另行通知
- 修复后重新跑 Pass 1 + Pass 2，直到全部通过

## 验证纪律

### 铁律：没有验证证据就不能声称完成

| 要声称 | 必须先做 | 不够的 |
|--------|---------|--------|
| "测试通过" | 跑测试命令，看到 0 failures | "应该能过"、上一次的结果 |
| "bug 修好了" | 复现原症状已消失 | "代码改了，应该好了" |
| "构建成功" | 跑构建命令，exit 0 | linter 通过不代表编译通过 |
| "需求实现完了" | 逐条对照需求清单 | "测试过了" |

### 禁止的措辞

在没有跑过验证命令之前，禁止使用：
- "应该可以了"、"看起来没问题"
- "Done"、"完成了"
- 任何暗示成功的表述

### 流程

```
1. 确定验证命令是什么
2. 执行完整命令（不是部分）
3. 读完整输出 + 检查 exit code
4. 输出确认了声称 → 才能说"完成"
5. 输出不确认 → 说实际状态，继续修
```

## 文档纪律

### 何时写设计文档

满足以下任一条件时，实现前先写设计文档：
- 新增独立功能模块
- 涉及 3 个以上文件的改动
- 需要做技术选型决策
- 影响已有接口契约

不满足时直接实现，不需要设计文档。

### 设计文档路径

```
docs/design/YYYY-MM-DD-<topic>.md
```

### 测试报告路径

```
docs/design/YYYY-MM-DD-<topic>-test-report.md
```

### 技术决策记录路径

```
docs/decisions/YYYY-MM-DD-<topic>.md
```

用于记录重要的技术选型决策（选了什么、为什么、否决了什么替代方案）。

## 不做的事

- 不为了通过 review 而降低代码质量（如加无用注释凑覆盖率）
- 不在 review 中提 Minor 级别以下的吹毛求疵
- 不重复检查已经确认通过的部分
- review 过程不需要通知用户，只需保证结果质量
